# 「良心商家」小程序 · 整体方案设计（V0.1，仅设计不实现）

> 定位：以编辑加工的公开信息为主体、用户打分为佐证的"商家对员工好不好"查询与传播工具。
> 一期形态：内容驱动的查询小程序 + 运营后台，不是 UGC 平台。

---

## 0. 已对齐的前提

| 项 | 结论 |
|---|---|
| 评分主体 | 平台编辑基于网络公开信息加工得出，用户打分只作佐证 |
| 身份校验 | 一期不做，用户评价不视为事实 |
| 数据规范性 | 一期允许商家名等不规范，但模型必须支持后续合并清洗 |
| 增长方式 | 热点案例驱动（胖东来、信誉楼、麦当劳中国等），分享卡片为核心传播载体 |
| 评价对象 | 一期只做品牌/集团级实体，不做门店级 |
| 一期不做 | OCR 识别、附近门店、员工身份验证、商家认证回应 |

## 1. 总体架构

```
┌──────────────┐   ┌──────────────┐   ┌──────────────┐
│  微信小程序   │   │  运营后台 Web │   │ 商家反馈表单  │
│  (用户端)     │   │  (编辑/审核)  │   │ (小程序内)    │
└──────┬───────┘   └──────┬───────┘   └──────┬───────┘
       └──────────────────┼──────────────────┘
                   ┌──────▼──────┐
                   │  业务 API    │
                   └──────┬──────┘
        ┌─────────────────┼─────────────────┐
┌───────▼──────┐  ┌───────▼──────┐  ┌───────▼──────┐
│  PostgreSQL  │  │  Redis       │  │  对象存储 COS │
│ 主库+全文/模糊│  │ 限流/缓存    │  │ 截图/附件/卡片│
└──────────────┘  └──────────────┘  └──────────────┘
                   ┌─────────────┐
                   │  采集管道    │  定时任务 → 抓取 → 去重 → LLM 抽取 → 入素材池
                   └─────────────┘
```

四个子系统：

1. **采集管道**：把外部信息变成"待审核素材"
2. **运营后台**：编辑把素材加工成"依据"，维护实体、评级、案例，处理商家工单
3. **业务 API + 存储**：统一数据模型与评级计算
4. **小程序**：查询、展示、打分、分享、反馈

## 2. 数据来源

### 2.1 信源分级

| 级别 | 来源 | 用途 | 采集方式 |
|---|---|---|---|
| **A 事实级** | 中国裁判文书网（劳动争议）、人社部拖欠工资失信联合惩戒名单、国家企业信用信息公示系统（行政处罚、年报参保人数）、信用中国、各地人社局公示 | 直接构成加/减分依据 | 定时爬取或手工检索，按统一社会信用代码匹配 |
| **B 权威报道级** | 人民日报/新华社/央视等央媒、财新/第一财经/界面/36氪等财经媒体、企业官方公告（公众号/官网/上市公司公告、ESG 报告） | 构成加/减分依据，需区分报道与软文 | 关键词监控 + RSS + 人工剪藏 |
| **C 舆情级** | 黑猫投诉、脉脉、看准网、小红书、抖音、微博、知乎 | 只能触发"存在争议"标签或作为线索，不能单独定级 | 反爬强，一期以人工监控 + 剪藏为主 |
| **D 线索级** | 自媒体转述、匿名帖、用户提交线索 | 仅作追查线索，不进评分 | 用户提交 + 人工 |

### 2.2 热点监控清单（hot_watchlist）

- 维护 30–50 个重点品牌 + 关键词（如"胖东来 分红""XX 欠薪"）
- 优先级分三档：P0 每小时、P1 每日、P2 每周
- 命中后进入素材池并推送运营（企业微信/飞书机器人）

### 2.3 一期预建实体库

编辑先手工建好 100–300 个品牌实体，覆盖：连锁餐饮、茶饮咖啡、零售商超、快递物流、互联网大厂、制造业头部。用户绝大多数搜索命中预建库，新建实体是少数路径。

## 3. 采集与加工流程

```
外部信源
  │
  ▼
① 抓取/剪藏 ─► raw_source（URL、标题、发布者、时间、摘要、截图）
  │
  ▼
② 去重 ─► URL hash + 标题相似度（同一事件多家转载合并为一个事件组）
  │
  ▼
③ LLM 抽取（二期自动，一期后台按钮触发）
     输出：涉及主体候选 / 事件类型 / 所属维度 / 正负向 / 事件日期 / 一句话摘要 / 置信度
  │
  ▼
④ 实体消歧 ─► 用 merchant_alias 模糊匹配，给出候选，人工确认
  │
  ▼
⑤ 生成 evidence 草稿（status = draft）
  │
  ▼
⑥ 人工审核 ─► 确认 / 修改 / 拒绝（一期负面依据 100% 人工确认）
  │
  ▼
⑦ 发布 ─► 触发评级重算 ─► 若总评跨档变化，需编辑二次确认后生效
```

### 3.1 采集合规约束

- 只存**标题 + 摘要 + 链接 + 截图**，不存全文，不做全文转载
- 遵守 robots 与访问频率，A 级政务站点优先走公开查询接口/手工
- 涉及个人（如被骂员工姓名）的内容在摘要中脱敏

### 3.2 剪藏工具（一期人工效率关键）

运营后台提供"粘贴链接 → 自动抓标题/发布者/时间/正文摘要/截图 → 预填 evidence 表单"的能力，是一期编辑最常用的入口。二期加浏览器插件。

## 4. 评级方法论

### 4.1 维度

| 维度 | 关注点 | 典型依据 |
|---|---|---|
| 薪酬与保障 | 按时发薪、社保覆盖、欠薪记录、分红/持股 | 参保人数比、欠薪名单、资产分配公告 |
| 工时与休假 | 工作制、带薪假、强制加班 | 官方制度公告、仲裁文书、媒体报道 |
| 尊严与文化 | 侮辱性管理、员工赋权、申诉机制 | 官方公告、仲裁文书、权威报道 |
| 争议与处罚 | 近 3 年仲裁/处罚/负面舆情 | A 级公示、B 级报道 |

### 4.2 计算规则（公开在"评级说明"页）

- 每条 evidence：`impact ∈ {+2, +1, -1, -2}` × `信源权重(A=1.0, B=0.8, C=0.3)` × `时间衰减(≤1年 1.0，1–3年 0.6，>3年 0.3)`
- 维度分 = 该维度所有已发布 evidence 加权求和，映射到五档
- 总评五档（编辑侧措辞，偏事实描述）：**标杆 / 良好 / 一般 / 存在争议 / 存在严重问题**
- 硬约束：
  - 无 A/B 级负面依据，不得进入"存在争议"以下两档
  - 仅 C 级负面 → 只能加"存在争议"**标签**，不改变总评
  - 总评跨档变化必须人工确认
  - 依据不足（<3 条 A/B 级）显示"信息不足"而非给分
- 每次重算生成 `rating_snapshot`，带 `rule_version`，规则变更可追溯

### 4.3 用户评价与平台评级的关系

- 物理分开展示、分开存储，用户评价不参与评级计算
- 用户侧五档用口语化措辞：**很好 / 推荐 / 还行 / 不推荐 / 极差**，避免与编辑侧措辞混淆
- 用户评价与平台评级明显背离（如平台"良好"但用户 60% 以上"不推荐"）时触发运营复核

## 5. 数据模型

### 5.1 实体与别名

```
merchant                      商家实体（品牌/集团）
  id, canonical_name, type(brand/group), industry, region,
  logo_url, unified_social_credit_code(可空), parent_id(可空),
  status(draft/pending/published/merged), merged_into_id(可空),
  created_by(editor/user), created_at, updated_at

merchant_alias                别名表（搜索命中主要靠它）
  id, merchant_id, alias, alias_normalized(去空格/大小写/全半角),
  source(editor/user/system), status(active/pending), created_at
  索引：pg_trgm 模糊索引 on alias_normalized

product_barcode               条形码 → 生产商（二期）
  barcode, product_name, merchant_id, source, status
```

**合并规则**：合并 A 到 B 时，A 的 alias、evidence、user_rating、merchant_feedback 全部迁移到 B，A 置为 `merged`，`merged_into_id = B`，写入 `merge_log`；对外 A 的 id 302 到 B。

### 5.2 素材与依据

```
raw_source                    原始素材
  id, url, url_hash(unique), title, publisher, source_level(A/B/C/D),
  published_at, fetched_at, summary, screenshot_url,
  event_group_id(去重分组), status(new/processing/used/discarded)

evidence                      依据（评级的最小单元）
  id, merchant_id, raw_source_id, dimension, polarity(+/-),
  impact(-2..+2), summary(≤120字), event_date,
  status(draft/approved/rejected/archived), reviewed_by, reviewed_at,
  merchant_reply_id(可空)     ← 商家回应挂在依据旁

rating_snapshot               评级快照
  id, merchant_id, dim_scores(jsonb), overall_level, tags(jsonb),
  evidence_count_ab, rule_version, computed_at, confirmed_by
```

### 5.3 案例内容

```
case_article                  热点案例
  id, title, subtitle, cover_url, body(富文本/markdown),
  timeline(jsonb: [{date, text, source_id}]),
  merchant_ids(jsonb), type(标杆/争议反转/负面警示),
  status, published_at, share_card_url, view_count, share_count
```

### 5.4 用户侧

```
user
  id, openid, unionid(可空), nickname, avatar, risk_score,
  created_at, last_active_at

user_rating                   用户打分
  id, user_id, merchant_id, level(1-5),
  identity_claim(customer/current_staff/former_staff/hearsay),
  comment(可空), comment_status(pending/approved/hidden),
  device_hash, ip_hash, weight(默认1.0，防刷降权),
  created_at, updated_at
  唯一约束：(user_id, merchant_id)  ← 一人一商家一票，可修改

user_tip                      用户提交线索
  id, user_id, merchant_id(可空), merchant_name_raw, url, text,
  images(jsonb), status(new/accepted/rejected), handled_by

merchant_feedback             商家反馈工单
  id, merchant_id, type(info_error/appeal_rating/add_positive/request_remove/other),
  contact_name, contact_phone, company_name,
  proof_files(jsonb: 营业执照/授权书), content, attachments(jsonb),
  status(new/reviewing/replied/closed), handled_by, reply, replied_at,
  created_at
```

### 5.5 运营与审计

```
hot_watchlist   merchant_id, keywords(jsonb), priority(P0/P1/P2), last_hit_at
merge_log       from_id, to_id, operator, reason, created_at
audit_log       operator, action, target_type, target_id, before(jsonb), after(jsonb), created_at
```

### 5.6 存储选型

- **PostgreSQL**：主库；`pg_trgm` 做别名模糊搜索；jsonb 存时间线/标签；一期不上 ES
- **Redis**：限流计数、热点缓存、分享卡片渲染队列
- **对象存储（腾讯云 COS）**：截图、附件、分享卡片图、logo
- 所有用户原始输入（商家名原文、评论原文）永久保留，不覆盖

## 6. 用户交互（小程序）

### 6.1 页面清单

| 页面 | 核心内容 |
|---|---|
| 首页 | 搜索框（主入口）、扫码入口（二期）、本周热点案例（3–5 条）、榜单入口 |
| 搜索结果 | 别名模糊匹配的候选列表（显示评级徽标）；无结果 → "补充这个商家" |
| 商家详情 | 见 6.2 |
| 案例文章 | 一句话结论 → 时间线（每条带来源）→ 关联商家评级卡 → 打分入口 → 分享 |
| 榜单 | 标杆企业榜 / 争议企业榜 / 按行业榜；每个榜单可生成分享图 |
| 打分弹层 | 见 6.3 |
| 商家反馈 | 见第 8 节 |
| 我的 | 我的评价、我的线索、评级说明、用户协议/隐私政策 |
| 评级说明 | 公开维度、权重、信源分级、时间衰减、硬约束 |

### 6.2 商家详情页结构（自上而下）

1. **头部**：名称、行业、地区、logo；平台总评（五档徽标）+ "最近更新 X 天前"
2. **维度卡片**：四个维度各自等级 + 依据条数
3. **依据列表**：按时间倒序，每条 = 维度标签 + 正负标识 + 摘要 + 来源名 + 日期 + 外链；有商家回应的在下方折叠展示
4. **用户怎么看**（视觉上明确分区，标"用户评价未经核实"）：五档分布条形图；按身份分层的小统计（顾客 N 人 / 自称员工 N 人）；精选已审核评论 3–5 条
5. **操作区**：打分、分享卡片、提供线索、我是商家/信息纠错
6. **底部**：免责声明、评级说明入口

### 6.3 打分流程

1. 选五档（很好 / 推荐 / 还行 / 不推荐 / 极差）
2. 自报身份单选（顾客 / 现员工 / 前员工 / 听说的），不校验
3. 可选文字（提示：不要写具体人名、联系方式；≤200 字）
4. 提交 → 走微信内容安全接口（msgSecCheck）→ 文字进入待审核
5. 提示"已收到，评分立即计入统计，文字审核后展示"
6. 同一商家可修改评分，保留修改历史

### 6.4 搜索与新建商家

- 输入 → 规范化（去空格、全半角、大小写）→ `pg_trgm` 匹配别名 → 返回候选
- 无匹配 → 引导"补充商家"：填名称（原文保留）+ 可选行业 → 系统再做一次模糊匹配提示"你是指 XX 吗？"→ 用户确认挂别名，否则建 `pending` 实体
- `pending` 实体对提交者本人可见，审核通过后公开

### 6.5 防刷（不做身份校验前提下的最低限度）

- `(user_id, merchant_id)` 唯一，一票可改
- 新用户 24 小时内最多 3 票；老用户每日最多 20 票
- 同一 `device_hash` / `ip_hash` 24 小时内对同一商家 ≥5 票 → 该批次 `weight` 降为 0.2 并告警
- 单商家 1 小时内评分量超过近 7 日均值 10 倍 → 告警 + 自动进入"观察"状态（统计延迟展示）
- 评论文字过内容安全接口 + 敏感词库

### 6.6 分享卡片

- 商家页、案例页、榜单页均可生成
- 内容：名称 / 总评徽标 / 2–3 条关键事实 / 小程序码 / "评级依据来自公开信息，详见小程序"
- 服务端渲染（无头浏览器或 Canvas），缓存到 COS，评级变化时失效重生成

## 7. 展示原则（对外一致遵守）

1. 平台评级与用户评价分区展示、措辞不同、不合并
2. 每条依据必须有来源名、日期、可点击外链
3. 评级规则公开，任何人可查
4. 时效标注：最近更新时间；>1 年事件标"历史事件"
5. 未审核的负面文字不对外展示
6. 依据不足时显示"信息不足"，不硬给评级
7. 商家回应与对应依据并列展示，不删原依据
8. 每页底部免责声明：信息来源于公开渠道整理，用户评价未经核实，如有异议请通过纠错入口反馈

## 8. 商家反馈入口

### 8.1 入口位置

- 商家详情页"我是商家 / 信息纠错"按钮
- 依据条目右侧"纠错"小入口（预填该依据 id）

### 8.2 表单

| 字段 | 说明 |
|---|---|
| 反馈类型 | 信息错误 / 申诉评级 / 补充正面材料 / 要求删除 / 其他 |
| 关联对象 | 商家（必填）、具体依据（可选） |
| 联系人 / 电话 | 必填，仅运营可见 |
| 企业证明 | 营业执照 + 授权书（图片），用于确认是商家本人；一期只做人工核对，不做 OCR |
| 说明 | 文字 ≤1000 字 |
| 附件 | 图片/PDF ≤5 个 |

### 8.3 处理流程

```
new → reviewing（运营领取）→ 处理动作 → replied → closed
```

处理动作四选一：

- **驳回**：给出理由（如"依据来自公开处罚记录，无法删除"）
- **修正依据**：修改摘要/日期/维度，写审计日志
- **新增依据**：商家提供的正面材料，按 B 级"企业官方公告"录入，正常参与评级
- **添加商家回应**：在依据旁展示商家说明，原依据保留

承诺：3 个工作日内首次响应。工单状态对提交者可见（通过手机号 + 工单号查询，或小程序内"我的反馈"）。

### 8.4 二期：商家认证

认证后可直接在商家页发布"商家回应"、更新官方制度信息（进入 B 级依据，仍需审核）。

## 10. 合规与风险控制

| 风险 | 对策 |
|---|---|
| 名誉权/商誉 | 负面评级必须有 A/B 级依据；依据带来源；公开纠错通道；商家回应机制；不做门店级负面 |
| 版权 | 只存摘要 + 链接 + 截图，不全文转载 |
| 个人信息 | 一期只收 openid，不收手机号（商家工单例外，仅运营可见）；隐私政策明示 |
| 内容安全 | 所有用户文字过微信 msgSecCheck + 自维护敏感词库；负面文字人工审核后展示 |
| 小程序类目 | 走"工具 – 信息查询"类目；内容定位为"企业公开信息汇总"，不自称新闻资讯；案例页避免新闻体措辞 |
| 备案 | ICP 备案；域名与服务器在境内 |
| 刷分与操纵 | 第 6.5 节防刷规则；用户评价不进评级 |
| 信源失效 | 依据保留截图；外链失效标注"原链接已失效，见截图" |

## 11. 技术选型建议

| 层 | 建议 | 理由 |
|---|---|---|
| 小程序 | 微信原生（一期）或 Taro | 一期只做微信，原生最省事 |
| 后端 | Python（FastAPI） | 采集、LLM 抽取、业务 API 同一语言栈 |
| 数据库 | PostgreSQL 15+ / pg_trgm | 模糊搜索 + jsonb，一期够用 |
| 缓存/限流 | Redis | |
| 对象存储 | 腾讯云 COS | 与小程序同生态 |
| 运营后台 | React + Ant Design Pro | 表格/表单密集型后台成熟方案 |
| LLM | 国内合规模型 API | 抽取摘要、主体识别、维度归类 |
| 采集 | Python 定时任务（APScheduler/Celery beat）+ Playwright（截图） | |
| 分享卡片 | 服务端 Playwright 渲染 HTML → PNG | 样式灵活、与前端复用 |
| 部署 | 腾讯云容器/轻量服务器 + Docker Compose | 一期规模小 |

## 12. 分期

### 一期（可上线的最小闭环）

- 预建 100–300 个品牌实体 + 别名
- 剪藏工具 + 依据人工录入与审核
- 评级计算与快照、评级说明页
- 10–20 个深度案例页（胖东来、信誉楼、麦当劳中国等 + 争议/负面案例）
- 小程序：搜索、商家详情、案例、榜单、打分、分享卡片、商家反馈表单、提供线索
- 后台：素材池、依据审核、实体管理（含合并）、评级管理、案例编辑、评价审核、工单
- 基础防刷、内容安全、免责声明、用户协议与隐私政策

### 二期

- 自动采集管道（A 级定时、B 级关键词监控）+ LLM 自动抽取草稿
- 热点监控推送
- 条形码 → 生产商实体
- 商家认证与商家回应
- 用户线索激励（被采纳后显示"线索贡献者"）
- 榜单细化（行业/地区）

### 三期

- 门店级实体与附近门店
- OCR 识别招牌/小票
- 员工身份验证（可选）
- 开放 API / 网页版
